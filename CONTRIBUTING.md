# Contributing

This model is early and meant to be pulled apart, not just read. A few ways to engage, roughly lightest to heaviest:

**Open an issue.** The lowest-friction way to contribute. Disagree with a definition, see a missing concept, or have a real scenario where a stage in the lifecycle doesn't map cleanly — open an issue and describe it in plain language. No particular format required.

**Comment on an existing issue.** If your feedback relates to something already open, adding your perspective there keeps the discussion in one place.

**Propose a new worked example.** The examples/ folder is meant to grow. If you have a real (or realistic, anonymized) initiative that would stress-test the model in a new domain, fork the repo, add a file under examples/ following the structure of the existing ones, and open a pull request.

**Propose a change to a concept.** If a definition, property, relationship, or rule in concepts/ should change, open a pull request with the edit and a short explanation of what scenario motivated it.

## Ground rules

- Plain language first. If a proposed change can't be explained to a non-technical operations person, it needs more work before it's ready.
- Real scenarios over hypotheticals. Feedback grounded in something that actually happened is more useful than abstract critique.
- Disagreement is welcome. The point of sharing this early is to find where it's wrong.
